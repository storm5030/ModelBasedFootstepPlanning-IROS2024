# 연구실 로봇 RL 코드에 더블 서포트 LIPM 이식하기

## 목적과 범위

현재 레포의 더블 서포트 데모를 참고하여, 연구실 로봇용 별도 RL 코드에 SSP/DSP 보행을 도입하기 위한 준비 문서다. 대상 코드 자체는 아직 검토하지 않았으므로 아래 내용은 확인 항목과 설계 제안이다. 현재 실행 코드는 변경하지 않는다.

이번 범위는 일반 고정 높이 LIPM의 더블 서포트다. 질량 스위칭, 몸통/발 질량 분리, 유효 CoM 계산은 포함하지 않는다.

참고 파일:
- LIPM/models/LIPM_3D_double_support.py
- LIPM/demos/demo_LIPM_3D_double_support.py
- LIPM/tests/test_double_support.py
- gym/envs/humanoid/humanoid_controller.py 및 humanoid_controller_config.py

## 1. 대상 코드에서 먼저 확인할 것

- 학습과 정책 재생이 같은 환경·플래너·토크 함수를 사용하는가.
- 실행 스크립트가 스텝 시간·명령·관측·랜덤화를 덮어쓰는가.
- CoM 상태가 실제 전체 질량중심인지, 루트/몸통 위치를 대용한 것인지.
- CoM 위치와 속도가 같은 물리량과 좌표계로 정의되어 있는가.
- 높이가 지면 기준인지 세계 좌표 z인지. 경사·단차 처리 여부.
- 정책 출력이 관절 목표, 토크, 잔차 행동 중 무엇인가.
- 위상, 좌우 스윙 표시, 접촉 스케줄과 실제 접촉 판정이 어디서 갱신되는가.
- 접촉·공중 시간·속도·발 위치 보상 및 종료 조건이 어디서 계산되는가.
- 환경별 리셋과 보행 시간 변경이 벡터화된 상태에 올바르게 반영되는가.

CoM을 새로 질량 분해할 필요는 없지만, 기존 상태 정의의 일관성은 확인해야 한다. 데모의 적분된 CoM을 실제 로봇 상태에 대입하지 않는다.

## 2. 시간과 상태 전환

평지, 일정 높이, 고정 접촉 시간의 첫 구현을 권장한다.

T_step = T_ss + T_ds
T_cycle = 2 * T_step

현재 비교용 후보는 T_ss=0.48초, T_ds=0.12초, 목표 속도 0.3 m/s다. 대상 로봇에 대한 최적값이나 안정성 보장값은 아니다.

권장 순서:
왼발 SSP → DSP(왼발에서 오른발로 하중 이동) → 오른발 SSP → DSP(오른발에서 왼발로 하중 이동).

- SSP: 한 발을 지지 상태로 유지하고 다른 발을 스윙한다.
- 착지 경계: 스윙 목표 위치와 높이에 도달한다. 데모에서는 정확히 지면에 도달하지만 실제 로봇 접촉은 별도 관측이다.
- DSP: 양발 접촉을 유지하며 다음 SSP의 지지발로 하중을 넘긴다.
- DSP 종료: 다음 SSP가 시작되며 반대 발을 스윙 대상으로 지정한다.

필요 상태 예: phase_type, phase_elapsed 또는 phase_count, support_side, next_support_side, phase_progress, dsp_progress. 기존 코드의 상태와 통합하여 중복된 카운터가 서로 어긋나지 않게 한다.

시간 기반 전환과 접촉 기반 전환 중 하나를 명확히 정한다. 첫 구현은 계획 시간 기반 전환으로 데모와 비교하고, 접촉 지연·조기 착지는 별도 로그로 본다. 안전한 접촉 확인/대기 로직이 이미 있다면 보존하되 최대 대기 시간과 실패 처리를 명시한다. 접촉 이벤트로 실제 시간을 늘리면 고정 시간 플래너의 예측도 다시 계산해야 한다.

## 3. 착지점 플래너

단순히 기존 SSP 사이에 대기 시간을 삽입하면 목표 평균 속도와 말단 상태가 달라진다. DSP의 ZMP 이동을 포함한 예측식을 사용한다.

h: 고정 CoM 계획 높이
omega = sqrt(g/h)
E = exp(omega*T_step)
K = expm1(omega*T_ds)/(omega*T_ds), T_ds=0이면 K=1

목표 보폭 s_d = 명령 수평 속력 * T_step.
목표 발너비 w_d는 두 발 사이의 전체 폭이다. s_d와 w_d를 반으로 나누지 않는다.

기존 데모의 목표 오프셋 크기:
b_x = K*s_d/(E-1)
b_y = K*w_d/(E+1)

현재 지지발 p와 다음 지지발 u를 사용하고 xi_rel = c_xy - p_xy + v_xy/omega라고 하면:
u_xy = p_xy + (E*xi_rel - b_next)/K.

b_next는 다음 지지측 부호와 보행 방향 회전을 반영한 2D 오프셋이다. 부호는 원 데모의 calculateFootLocationForNextStepXcoMWorld를 기준으로 검증한다.

DSP 참조 ZMP:
p_zmp(s) = (1-s)*p_old + s*p_new, s∈[0,1].

이 ZMP는 계획 모델의 입력이다. RL 환경에서 실제 ZMP가 이 경로를 정확히 따라간다고 가정하면 안 된다. 물리 시뮬레이션과 정책의 접촉력 결과를 별도로 측정한다. 토크 제어나 ZMP 추종 제어기를 이번 작업에 자동 추가하는 것은 아니다.

데모는 NumPy 단일 환경 코드다. 대상 환경이 Torch/GPU 배치 구조면 수식을 벡터화해 옮기고, 환경별 로봇 객체 생성이나 CPU 왕복은 피한다.

## 4. 정책 관측과 행동

관절 제어 방식은 우선 유지한다. 정책이 현재 DSP라는 것을 구분할 수 있는 관측을 제공해야 한다.

선택지:
- 기존 sin/cos 전체 위상으로 SSP/DSP 구간을 명확히 구분하도록 스케줄을 정의.
- 명시적인 SSP/DSP 플래그와 구간 진행률을 추가.

고정 T_ss/T_ds에서는 기존 주기 위상만으로 상태가 결정될 수 있다. 접촉에 따라 DSP를 연장하거나 시간을 랜덤화하면 기존 위상만으로 충분한지 다시 확인한다. 관측을 추가하면 네트워크 입력 차원과 체크포인트 호환성이 바뀐다.

스윙 궤적을 명시적으로 제공하는 코드라면 SSP에서만 스윙 진행률을 증가시키고 DSP에서는 발 목표를 지면에 유지한다. SSP 끝의 발 속도를 0에 가깝게 연결한다. 정책이 관절 동작을 직접 생성하는 코드라면 발 높이를 하드코딩으로 강제하지 말고 접촉·높이 참조 및 보상으로 표현한다.

## 5. 보상 점검

현재 레포의 contact_schedule 보상은 (오른발 접촉 - 왼발 접촉) * 주기 스케줄에 기반한다. 양발 접촉이면 이 차이가 0이므로 DSP의 올바른 접촉을 직접 보상하지 않는다. 이 형태를 대상 코드가 사용한다면 재설계가 필요하다.

권장 방향은 좌우 발 각각의 접촉 목표를 정의하는 것이다.

| 구간 | 왼발 접촉 목표 | 오른발 접촉 목표 |
|---|---:|---:|
| 왼발 SSP | 1 | 0 |
| DSP | 1 | 1 |
| 오른발 SSP | 0 | 1 |

단순 이진 접촉 판정은 하중이 0으로 가는 전환 경계에서 흔들릴 수 있다. 발별 접촉력 임계값, 필터/히스테리시스, 경계 허용 폭을 대상 센서·시뮬레이터에 맞춘다. 정확한 경계에서 양발에 동시에 큰 최소 하중을 요구하지 않는다.

| 항목 | 확인·수정 방향 |
|---|---|
| 접촉 스케줄 | SSP는 한 발, DSP는 양발을 올바른 상태로 평가 |
| 스윙 높이·발 들기 | SSP에서만 요구, DSP에서 발 들기를 유도하지 않음 |
| 공중 시간 보상 | DSP 연장과 충돌하지 않도록 적용 구간·목표시간 조정 |
| 발 위치·방향 | SSP 착지와 DSP 유지에 맞춰 평가, 전환 시 목표 인덱스 확인 |
| 발 미끄러짐 | 하중이 실린 접촉발의 수평 속도 억제, DSP에서는 양발 대상 |
| 충격·접촉력 | 착지 충격과 과도한 힘은 억제하되 하중 전환을 방해하지 않음 |
| 속도 추종 | 기존 유지, 첫 구현에서 가중치를 동시에 크게 바꾸지 않음 |
| 자세·높이·토크·행동 변화 | 기존 유지, DSP 관련 항목과 충돌 여부 확인 |
| 종료 조건 | 정상 양발 접촉을 실패로 판정하지 않는지 확인 |

DSP 하중 비율 참조를 추가할 수 있으나 첫 이식의 필수조건은 아니다. 우선 발별 접촉 목표와 발 목표 유지부터 구현하고 실제 접촉력 로그를 확인한다. 한쪽 발에 거의 하중이 없는데 접촉 불리언만 참인 경우를 별도로 확인한다.

보상 가중치 숫자는 대상 코드의 정규화, dt 스케일링, 기존 보상 크기를 본 뒤 결정한다. DSP를 보상한다고 양발을 계속 붙이고만 있는 정책이 유리해지지 않도록 SSP 스케줄·속도·발 목표를 함께 확인한다.

## 6. 출발과 리셋

일반 DSP 보행 추가와 정지 출발 설계는 분리한다.

현재 레포의 RL은 초기 제자리 양발 목표를 주고 일정 시간이 지난 뒤 첫 XCoM 목표를 생성한다. 대상 코드에도 비슷한 출발 구조가 있다면 먼저 보존하여 DSP만의 효과를 비교한다.

데모의 periodic-start를 실제 로봇 리셋에 그대로 넣지 않는다. 이는 이미 걷는 상태의 수평 위치·속도를 초기값으로 주는 비교용 기능이다. 정지한 실제 로봇의 출발을 대신하지 않는다.

첫발 안정성은 초기 위상, 제자리 목표 유지 시간, 첫 스윙측, CoM 초기속도, 접촉 보상으로 함께 결정된다. 출발 DSP를 명시적으로 추가한다면 정상 보행 DSP와 다른 시간을 설정할 수 있게 한다. 초기화 시 모든 카운터·발 목표·접촉 이력을 일관되게 리셋한다.

## 7. 학습 및 재생

플래너 입력이 같은 모양이어도 DSP 추가는 접촉 스케줄과 참조 분포를 바꾼다. 기존 체크포인트로 재생하는 것은 진단용이며 성능 보장을 의미하지 않는다. 재학습 또는 파인튜닝을 계획한다.

학습과 재생에서 같은 플래너 선택, T_ss/T_ds, 관측 정의, 접촉 스케줄을 사용한다. 재생 스크립트의 시간 덮어쓰기와 과거 코드 로딩 옵션을 확인한다.

첫 비교에서는 속도·높이·총 스텝 시간·랜덤화·보상 변경 범위를 통제한다. 예를 들어 기존 SSP 0.6초와 새 SSP 0.48초 + DSP 0.12초를 비교하면 전체 스텝 주기를 유지할 수 있다.

## 8. 이식 순서와 검증 기준

1. 대상 코드의 관측, 상태, 행동, 접촉 보상, 리셋, 실행 설정을 먼저 매핑한다.
2. DSP 시간 0의 새 플래너가 기존 식과 일치하는지 검사한다.
3. SSP/DSP 상태와 스윙 시간·관측 스케줄을 연결한다.
4. DSP를 포함한 착지점 식을 연결한다.
5. 접촉·발 높이·공중 시간 보상의 모순을 제거한다.
6. 소수 환경에서 출발 및 몇 스텝의 상태·보상을 기록한다.
7. 학습 또는 파인튜닝 후 같은 명령과 조건으로 비교한다.

필수 로그:
- phase_type, 구간 진행률, 다음 지지측, 발 목표
- 실제 양발 접촉 및 수직 접촉력
- CoM/루트의 명확히 구분된 위치·속도
- 계획 ZMP와 측정/추정 ZMP(가능할 경우)
- 실제 발 위치·높이·속도, 접촉 미끄러짐
- 보상 항목별 값, 종료 이유

검증 기준:
- SSP에서 지지발이 유지되고 DSP에서 계획상 양발이 지면에 머무는가.
- DSP가 정책의 실제 접촉에서도 형성되는가. 위상 표시만 DSP인지 구분한다.
- 초기 출발에서 큰 착지 목표·속도 과도응답이 생기지 않는가.
- 일정 명령의 완전한 보행 주기 평균 속도 및 실제 보폭이 맞는가.
- 보상 변경 후 발을 끌거나, 양발을 계속 붙이거나, DSP를 회피하지 않는가.
- 발 미끄러짐, 충격, 넘어짐 비율이 기존 정책 대비 어떻게 변하는가.

새 플래너의 데모 검증은 전체 로봇 안정성 검증이 아니다. 특히 데모의 선형 ZMP 참조와 정책이 실제로 만드는 하중 이동을 분리해서 평가해야 한다.
